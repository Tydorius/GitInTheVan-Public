Repo: `E:\github\LLM-Intercept\GitInTheVan`. Rules: no git actions (2), additive migration (10), debug captures on new stages (16), minor bump (9). Design ref: `Planning/project-plan.md:2295-2407`.

## Two decisions locked from our discussion

1. **Failover never stops early.** Every failure — any HTTP status ≠ 200, any exception (401, 404, 500, 429, timeout, connection error) — advances to the next candidate. Only total exhaustion returns an error (503). No retryable/non-retryable distinction. Each candidate carries its own model/api_key/provider/base_url/bypass_method (so a free OpenRouter key can fall through to a paid endpoint with a different model).
2. **Eager-load the chain, then release the DB.** One query returns the ordered candidate list; the DB session closes before any upstream call. Rationale: upstream calls run up to 300s (`request_timeout=300`); lazy-loading would hold/reopen pooled DB connections (pool size 10) across those long calls → pool starvation at scale. One query returning N tiny rows is also cheaper than N queries of 1 row each. The failover loop iterates a pure in-memory list (simple, testable, no async DB mid-loop).

```
    re-stash ALL per-candidate fields onto body_json:
        _gitv_provider, _gitv_base_url, _gitv_api_key, model, bypass_method
    try:
        response_data, status = await _do_forward(...)
        if status == 200: return (response_data, 200)   # success
        log + emit <think><gitv>"X" returned Y, trying next</think><gitv>

        log + emit <think><gitv>"X" failed, trying next</think><gitv>

return (error_body, 503)                      # all exhausted
```

- DB connections never held across upstream calls.
